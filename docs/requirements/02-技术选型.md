## 二、PDF 生成方案对比（核心决策）

### 2.1 方案对比

| 方案 | 原理 | 输出质量 | 包体积 | 离线 | 文字可选中 | 推荐度 |
|------|------|----------|--------|------|-----------|--------|
| **Paged.js + CSS print** | W3C 分页媒体 polyfill + 浏览器打印 | 高 | ~100KB | Yes | Yes | ★★★★★ |
| **@react-pdf/renderer** | React 声明式 PDF 文档 | 高 | ~500KB | Yes | Yes | ★★★★ |
| **html2pdf.js** | html2canvas 截图 + jsPDF | 中（栅格化） | ~1.2MB | Yes | **No** | ★★ |
| **pdfmake** | 声明式 JSON → PDF | 高 | ~300KB | Yes | Yes | ★★★ |
| **Puppeteer（服务端）** | Chrome 渲染 | 极高 | N/A | No | Yes | N/A（不符定位） |

### 2.2 推荐方案：Paged.js + CSS @media print

**理由**：
- 符合 W3C 分页媒体标准，是浏览器端分页的未来方向
- 包体积极小（~100KB），完美匹配离线 PWA 定位
- 输出为矢量 PDF，文字可搜索/可选中
- 通过 CSS `@page` 规则精确控制页面大小、边距、页眉页脚
- 天然与 CSS 主题系统集成，预览即所得

**风险**：
- 不同浏览器的打印引擎存在差异（Chrome 最佳，Firefox/Safari 次之）
- 需要针对各浏览器测试

### 2.3 备选方案：@react-pdf/renderer

**适用场景**：如果 Paged.js 在某些场景无法满足需求（如复杂表格跨页），可切到 @react-pdf/renderer。

**注意**：中文字体文件较大（Noto Sans SC ~16MB），需做字体子集化或懒加载。

## 三、Markdown 解析方案对比

| 库 | 周下载量 | 扩展性 | GFM | 数学公式 | 代码高亮 | 维护状态 |
|------|---------|--------|-----|---------|---------|---------|
| **unified/remark** | ~10M+ | 极高（AST 管线） | remark-gfm | remark-math + rehype-katex | rehype-highlight | 非常活跃 |
| **markdown-it** | ~15M+ | 高（插件） | 内置 | markdown-it-katex | markdown-it-highlightjs | 稳定 |
| **marked** | ~12M+ | 中等 | 内置 | marked-katex-extension | 有限 | 活跃 |
| **showdown** | ~1.5M | 中等 | 内置 | 有限 | 有限 | 低活跃 |

### 推荐：unified/remark 生态

**核心理由**：
1. 基于 AST 的管线架构（Markdown → MDAST → HAST → HTML），每个阶段可插入自定义 transformer
2. 插件生态最丰富：remark-gfm、remark-math、rehype-highlight、rehype-slug、remark-emoji 等
3. 是 Next.js、Astro、Remix 等现代框架的标准选择
4. 由 unified 集体维护，长期可持续

**核心插件清单**：
```
remark-gfm          — GFM（表格、删除线、任务列表、自动链接）
remark-math         — LaTeX 数学公式
rehype-katex        — 公式渲染
rehype-highlight    — 代码高亮（基于 AST）
rehype-slug         — 标题锚点
rehype-autolink-headings — 标题自动链接
remark-frontmatter  — YAML frontmatter 解析
remark-emoji        — Emoji 支持
```

## 四、代码编辑器选型

| 特性 | **CodeMirror 6** | **Monaco Editor** |
|------|-------------------|-------------------|
| 包体积 | ~150-200KB（按需） | ~4MB（压缩 ~1.5MB） |
| 移动端 | 原生支持 | **不支持** |
| Markdown 支持 | 内置 GFM 模式 | 内置语言服务 |
| 性能（大文件） | 优秀 | 优秀（内存更高） |
| 可访问性 | 优秀 | 一般 |
| React 集成 | @uiw/react-codemirror | @monaco-editor/react |
| 离线适配 | 极佳 | 一般（Web Workers） |

### 推荐：CodeMirror 6

**核心理由**：
1. 体积小 10 倍+（~200KB vs ~4MB），符合离线 Web App 定位
2. 原生移动端支持
3. 当前项目已用 CM5，概念延续
4. 函数式组合架构，扩展性强

**核心包**：
```
@codemirror/lang-markdown   — Markdown 语言模式
@codemirror/lang-gfm        — GFM 扩展
@uiw/react-codemirror       — React 集成
@codemirror/theme-one-dark  — 暗色主题
```

## 五、前端框架与构建工具

### 推荐：Vite 6 + React 19

| 维度 | 选择 | 理由 |
|------|------|------|
| 构建工具 | Vite 6 | CRA 已废弃，Vite 开发/构建速度快 5-10x |
| 框架 | React 19 | 并发特性、Compiler 自动 memoization |
| 状态管理 | Zustand (~1KB) | 状态简单（文本 + UI），无需 Redux |
| CSS | Tailwind CSS v4 | 实用类快速构建，零运行时开销 |
| PWA | vite-plugin-pwa | 替代当前 Workbox 集成，配置化 |
| 图标 | Lucide React | 轻量、树摇友好 |

**为什么不用 Next.js**：
- Printdown 不需要 SSR/SSG/API Routes
- 离线 PWA 在 Next.js 中需额外配置
- 引入不必要的复杂度

## 七、关键风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 中文字体嵌入体积大 | 加载速度 | 字体子集化 + 懒加载 |
| CM5→CM6 API 完全不同 | 开发成本 | 全新编写，非迁移 |
| 不同浏览器打印差异 | PDF 一致性 | 针对主流浏览器测试 + Chrome 推荐提示 |
| Paged.js 社区维护 | 长期稳定性 | CSS @page 是标准，即使 Paged.js 停维也有浏览器原生支持兜底 |
| 离线资源缓存完整性 | PWA 可靠性 | 严格测试 Service Worker 缓存策略 |
